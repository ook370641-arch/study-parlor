Claude Code 记忆四层架构

从静态指令到自动提取，从跨会话持久化到单会话压缩，再到上下文压缩的双路径决策

三层架构全景

Claude Code 的记忆不是"一个东西"，而是三个独立机制的分层协作：

Layer 1: 静态指令（CLAUDE.md）
你手动编写的规则文件，分 4 级优先级。
作用：告诉 Claude "应该怎么做"。
生命周期：永久，除非你手动删。
Layer 2: Auto Memory（自动记忆）
后台子 agent自动从对话中提取。
作用：记住"你是谁、你喜欢什么"。
生命周期：跨会话持久化，存为 .md 文件。
Layer 3: Session Memory（会话记忆）
后台子 agent在对话进行中定期更新。
作用：本次对话太长时，把被压缩掉的历史替换成摘要，模型还能知道之前聊了什么。
生命周期：单会话临时文件，会话结束即失效。
Layer 4: Compact（上下文压缩）
两条路径的压缩决策树：Session Memory 快速路径（本地文件读取）vs Traditional 传统路径（LLM 实时生成 9-section 摘要）。
作用：当用户手动输入 /compact 或 token 超过阈值自动触发时，精简上下文，让对话能继续。
生命周期：即时执行，替换历史消息为摘要 + 重建附件。

CLAUDE.md 四层优先级系统

这 4 层不是"4 个文件"，而是4 个搜索路径。Claude Code 启动时会按顺序查找，把找到的文件内容拼进系统提示词。

核心法则：加载顺序是 Managed → User → Project → Local，但后加载的在 prompt 中排在更后面。LLM 对越靠后的内容注意力越高。所以 Local > Project > User > Managed。

↓ 后加载，优先级更高

Auto Memory（自动记忆）

不是主 agent 直接写文件，而是通过一个后台 fork 的子 agent，在每轮完整对话结束后自动从近期消息中提取值得记住的信息。

主 Agent 与用户对话
→
对话结束 handleStopHooks
→

→
读取现有记忆 scanMemoryFiles
→
提取 + 写入 FileWriteTool

关键设计

1. 互斥机制（Mutual Exclusion）

如果主 agent 自己在对话中用了 Write/Edit 工具写了 memory 文件（比如用户说"记住我是 AI PM"），后台提取 agent 检测到后会直接跳过。两者是"互斥"关系——主 agent 写过了，后台就不用再写。

2. 四类型分类系统

提取 agent 把记忆分为 4 种类型，每种有明确的保存时机和使用方式：

  • user — 用户角色、目标、知识水平（如"用户是 AI PM，零代码基础"）
  • feedback — 用户对 Claude 的反馈（如"不要总结，我看得懂 diff"）
  • project — 项目进展、截止日期、背景（如"移动团队周四切 release"）
  • reference — 外部系统指针（如"bug 在 Linear INGEST 项目里追踪"）

3. 写入两步走

Step 1：写独立的 .md 文件（如 user_role.md），带 frontmatter（name/description/type）。
Step 2：在 MEMORY.md 索引里加一行指针：- [Title](file.md) — 一句话描述。

Session Memory（会话记忆）

这也是通过后台 fork 子 agent运行的，但目的完全不同：它不是"记住你下次来还能用"，而是"本次对话太长时，把被压缩掉的内容替换成摘要"。

主 Agent 与用户对话
→
达到阈值 token > 10000
或 tool calls > N
→
Fork 子 Agent post-sampling hook
→
读取当前笔记 summary.md
→
Edit 更新 FileEditTool

关键设计

1. 触发条件（阈值控制）

不是每轮都触发，而是满足以下条件时才触发：

  • 初始化阈值：对话 token 超过 ~10000 时，第一次创建 session memory
  • 更新阈值：之后每增加 ~5000 token，或每 N 个 tool call，更新一次
  • 安全条件：最后一轮 assistant 没有 tool call 时才提取（避免中断工具链）

2. 文件结构（9 个固定章节）

Session Memory 是一个 summary.md，有固定的 9 个章节：

# Session Title — 会话标题
# Current State — 当前在做什么
# Task specification — 用户要做什么
# Files and Functions — 重要文件
# Workflow — 常用命令
# Errors & Corrections — 错误和修复
# Codebase Documentation — 系统组件
# Learnings — 经验教训
# Key results — 关键输出
# Worklog — 工作记录

3. 为什么你在本地找不到它？

Session Memory 的存储路径是：

~/.claude/projects/{项目名}/{sessionId}/session-memory/summary.md

它在 会话子目录里，不是 memory/ 目录。而且：

  • 它被设计为临时文件，会话结束后就失去意义
  • 它用于上下文压缩——当对话太长装不下时，用 session summary 替代被丢弃的历史消息
  • 它不跨会话——下次开新会话，会创建新的 session memory

Compact（上下文压缩）

当对话历史太长、token 窗口接近满载时，Claude Code 会把旧消息压缩成摘要，腾出空间让对话继续。/compact 命令和自动 compact 共用同一套双路径决策树——不是每次都走 LLM，而是先尝试一条本地快速路径。

→

本地文件读取
→
成功？ 快速返回摘要
→
Path B Traditional
LLM 实时生成

关键设计

1. 双路径决策树

每次 compact 先走 Path A，失败才走 Path B。两条路径的核心差异：

  • Path A — Session Memory Compaction：读取预维护的 summary.md，本地做数组切片，无 API 调用。条件：无自定义 compact 指令 + GrowthBook 双开关（tengu_session_memory + tengu_sm_compact）均开启（默认均 false）。
  • Path B — Traditional Compaction：先执行 microcompact 清理旧工具结果，再 runForkedAgent(maxTurns: 1) 让 LLM 生成 9-section 结构化摘要，失败则 fallback 到流式 API。
这就是为什么你的 /compact 总是很慢：Path A 的两个 GrowthBook 开关默认都是 false，所以绝大多数用户走的都是 Path B——LLM 要通读整个对话历史，按时间顺序逐条分析，再写一份包含 9 个章节的详细摘要。这份"作业"的量级，和让 LLM 写一篇技术综述差不多。

2. Microcompact 预处理

在把消息送给 LLM 摘要之前，先做一次"轻量清理"，减少 token 负担：

  • Time-Based Microcompact：如果距离最后一条 assistant 消息的时间超过阈值，把旧的 tool result content 替换成 [Old tool result content cleared]，保留最近 N 个可压缩的工具结果
  • Cached Microcompact：不修改本地消息，通过 cache_reference + cache_edits 在 API 层标记哪些工具结果可以被忽略，由服务端处理
  • 可压缩工具白名单：FileRead、Bash/PowerShell、Grep、Glob、WebSearch、WebFetch、FileEdit、FileWrite 等"读取类"工具结果可以被清理；用户消息、assistant 回复、tool_use 指令不会被碰

3. 9-Section 摘要结构

Path B 的 LLM 被强制要求先写一个 <analysis> 草稿块（最终被 strip），再输出 <summary> 正式摘要。摘要必须包含 9 个固定章节：

1. Primary Request — 用户的所有显式请求和意图
2. Key Technical Concepts — 所有重要技术概念
3. Files and Code — 文件、代码片段、函数签名
4. Errors and Fixes — 错误和修复方法
5. Problem Solving — 已解决问题和持续排查
6. All User Messages — 所有非工具结果的用户消息
7. Pending Tasks — 明确的待办任务
8. Current Work — summary 前正在做什么
9. Optional Next Step — 下一步该做什么，必须包含对话中的直接引用（verbatim）以防任务漂移

4. Post-Compact 附件重建

压缩完成后，被丢弃的不只是旧消息——还有各种附件也需要重新注入上下文，否则模型会"失忆"：

  • 最近访问的文件：最多 5 个文件，总预算 50K tokens，单个文件上限 5K tokens
  • Skills：总预算 25K tokens，单个 skill 上限 5K tokens（保留文件顶部通常最关键）
  • Plan Mode 附件：当前 plan 文件路径和内容
  • Deferred Tool Delta：待处理的工具变更通知
  • Session Start Hooks：会话启动时的系统级上下文
