# 内部技术备忘录：Claude Code Agent Harness 为何表现更优——架构深度对比

**撰写人**：技术研究助手  
**日期**：2026 年 8 月  
**范围**：对比 Claude Code、Cursor、GitHub Copilot、Devin 的 agent harness 架构差异，聚焦“为什么 Claude Code 在复杂自主任务中一致领先”的根本原因。

---

## 1. 什么是 Agent Harness，以及它为何决定表现

Agent harness 是将语言模型转化为能真实操作环境、执行工具、管理上下文并遵守安全边界的“代理”的**基础设施层**。它不等于模型本身，而是模型周围的“数字肢体与中枢神经系统”。一份公认的定义将其拆为九个核心组件：模型接口、工具注册表、上下文管理器、规划模块、执行引擎、记忆系统、反馈循环、安全护栏和编排层 [R1-2]。改变 harness 设计，即使不改模型，也能带来 **6 倍的性能差异** [R1-18]。

对编程场景，harness 决定模型如何读取文件、生成 diff、执行 bash 命令、跨多步保持连贯，以及何时压缩对话。Claude Code、Cursor、Copilot、Devin 的深层分歧，不在模型强弱，而在 harness 设计哲学与工程取舍 [R1-3][R2-17]。

## 2. 核心架构差异：为什么 Claude Code 的 Harness 更胜一筹

以下是四款工具的 harness 关键维度对比，数据来自 2026 年多个实测报告与官方文档。

| 维度 | Claude Code | Cursor | GitHub Copilot | Devin |
|------|-------------|--------|----------------|-------|
| **运行模式** | 终端驻留本地代理，每个重要操作请求显式同意 [R1-3] | IDE 内代理，支持后台/云代理（3.0 八代理并行）[R2-4] | IDE 内代理模式，依赖编辑器集成 [R1-9] | 全自主云代理，容器隔离，无实时人工干预 [R1-3][R1-11] |
| **代理表现社区共识** | 自主代理工作最强 [R1-9][R2-2] | IDE 内多文件编辑强，自主长任务较弱 [R2-12] | 代理模式成熟度最低 [R1-9] | 适合明确、重复的长任务，实时开发不如 [R1-16] |
| **上下文窗口与管理** | 200K 令牌；在 80-90% 占用触发智能压缩，保持关键信息 [R2-11]；子代理隔离上下文 [R2-20] | 宣称 200K，实测有效 70-120K [R2-12]；不同压缩策略，易丢失跨文件连贯 [R2-11][R2-12] | 窗口较小，代理模式下多文件状态易丢失 [R1-9] | 全 repo 克隆入 VM，背景丰富但可能产生架构误判 [R2-14] |
| **扩展性 / 控制面** | **Hooks（20+ 生命周期事件）+ Skills + MCP + 子代理/Teams**，四层分层，各自承担不同上下文成本 [R2-6][R2-8] | 支持 MCP，有基础 hooks 但**不能阻止或修改工具调用** [R2-9][R2-11] | 有限 MCP，依赖 Copilot 扩展，无 hooks 或自定义代理框架 [R1-10] | 内部规划器和工作流，对外不透明，无直接扩展机制 |
| **权限与安全护栏** | 每步可阻塞，hook 在上下文外执行，可调用独立模型进行验证 [R2-7][R2-9] | 事后通知，不阻塞 [R2-9] | 基本权限模型，无外部验证钩子 | 沙箱容器，安全但只依赖自身规划 |
| **长期任务持久力** | 单次会话完成大型重构，保持上下文连贯；Ralph Loop 模式强制继续直到完成 [R1-16][R2-12] | 频繁需要重新提示，跨文件丢失上下文 [R2-12] | 不适于复杂长任务 | 适合数小时后台任务，但缺乏实时纠偏 [R1-16] |
| **模型与 Harness 联合优化** | 模型针对 harness 期望的动作（文件系统、bash、规划、子代理分发）进行后训练 [R1-5] | 模型训练未深度绑定 Cursor 的 harness 特征 | 依赖通用 Copilot 模型，未针对代理工具链微调 | 使用定制规划模块，但模型调用封装较重 [R2-17] |

**核心结论**：Claude Code 并非赢在单一“大招”，而是通过 **hooks 作为零成本决定论安全网**、**对上下文窗口成本敏感的四种扩展机制**、以及**与模型后训练的深度耦合**，构建了一个比其他工具更完整、更不易退化的代理运行时。

## 3. 决定性差异一：Hook 架构——决定论的“外骨骼”

Claude Code 的 hook 系统是其 harness 最被低估的武器。它提供超过 **20 种生命周期事件**（如 `PreToolUse`、`PostToolUse`、`Stop`），支持 4 类处理器，最重要的是：**hooks 运行在模型上下文之外，可独立指定另一个 AI 模型验证 Claude 的输出 [R2-7]**。例如，在写入文件前强制运行 lint 检查，若失败则**阻塞操作并改写参数**，而不依赖于模型遵守指令（那是不确定的）。Cursor 的 hooks 只能观察，无法阻断或干预 [R2-9]。

这种“上下文外的决定论控制”让 Claude Code 能实现 LangChain 所描述的 **Ralph Loop** 等高级模式：当代理试图终止某任务但实际未完成时，hook 拦截退出信号，注入原目标清空上下文重新开始，迫使代理继续工作直至满足完成条件 [R1-16]。这种模式不可能纯靠提示工程可靠实现。

## 4. 决定性差异二：上下文管理的取舍哲学

两者均拥有大上下文窗口，但 **压缩时机与策略** 拉开了差距。Claude Code 在上下文使用率达到 **80-90%** 时触发压缩 [R2-11]，它优先保留当前任务关键信息、工具调用结果和结构化摘要，丢弃冗余聊天轮次。而 Cursor 的压缩策略更激进或保守？实测中，Cursor 随代理任务推进逐渐丢失跨文件的类型关系，导致需反复多轮重新提示；同一份大重构，Claude Code 单次会话完成，Cursor 却频繁失忆 [R2-12]。

此外，Claude Code 的 **子代理模型** 保证了上下文隔离：每启动一个子代理执行子任务，它获得一个干净的上下文窗口，完成后只返回摘要给主会话 [R2-20]。这避免主会话被临时推理和大量文件内容污染，使长期计划保持清醒。Copilot 和 Cursor 尚缺乏同等机制。

## 5. 决定性差异三：与模型的共生演化

Addy Osmani 指出一个被忽略的事实：**今天的代理产品与特定 harness 一起进行后训练** [R1-5]。即 Opus 4.6 在 Claude Code 内格外擅长使用 bash、编辑文件、调度子代理，不是因为模型本身学到这些，而是训练数据里包含了 Claude Code harness 的具体工具调用格式和交互模式。当同一个模型在其他 harness 里运行时，工具逻辑和反馈信号的变化会导致隐藏的回归。这构成了护城河：Cursor 切换底层模型或 Copilot 叠加代理功能，都无法轻易复现这种精确拟合。

对比之下，Cursor 的代理模式使用模型时，依赖更通用的指令格式，未针对 harness 细节进行同等程度的微调 [R2-11][R1-5]。Devin 则完全走另一条路，给模型套上自身的规划基础设施，但代价是降低了模型决策自由度，性能更依赖工程管线而非模型原生能力 [R2-17]。

## 6. 表格对比：任务执行模式的优劣

| 场景 | Claude Code | Cursor | Copilot | Devin |
|------|-------------|--------|---------|-------|
| 小范围多文件编辑（10 文件内） | 优秀，配合 hooks 更安全 | **最佳**，内联体验流畅 [R1-12] | 需手动干预，文件创建差 [R1-12] | 过重，不适用 |
| 大型重构（跨 repo） | **一次会话自主完成** [R2-12] | 频繁重提示，上下文丢失 [R2-12] | 无法胜任 | 可尝试，但无实时纠正 |
| 长时间异步任务（数小时） | 可通过后台代理由 CI/CD 触发 [R2-13] | 云代理可用，但上下文易偏航 | 不支持 | **最强**，但 PR 质量依赖需求清晰度 [R1-16] |
| 安全敏感操作 / 合规要求 | hooks 强制阻塞/审计，call-out 外部模型 [R2-9] | 弱通知，不可阻断 | 弱 | 沙箱隔离，缺乏细粒度审计 |

**值得注意的矛盾**：SitePoint 的实测显示 Claude Code 和 Cursor 在自主完成 8 文件任务时输出质量相当 [R1-12]，但这与多个来源报告的大规模任务中 Cursor 失忆相悖 [R2-12]。推测原因在于任务规模——小规模、边界清晰的任务中，两者差异不大；一旦上下文需求飙升（大量文件交互、长期对话），Cursor 压缩策略和低级 hooks 限制导致表现劣化。因此，**判定“表现更好”需指定条件**：Claude Code 在需要长逻辑链、跨文件强依赖的自主动作中优势显著。

## 7. 关键收获（Takeaways）

1. **Harness 的差异是结构性的，不是模型强弱**：Claude Code 领先在于 hooks 决定论层、上下文管理策略、与模型后训练绑定，而非单纯模型更强。
2. **Hooks 是“上下文外的安全网”**：允许在模型决策前后插入决定论逻辑，这是 Cursor 和 Copilot 目前无法实现的控制粒度，也是生产环境可信任度的最关键支撑。
3. **扩展机制必须考虑上下文成本**：Claude Code 用四种机制（hook 零成本、skill 轻量、MCP 按需、子代理隔离）应对不同需求，是工程上权衡的体现。
4. **长期任务的表现由上下文管理定义**：压缩时机（80-90% 满载）和子代理隔离决定了代理是否会“忘记自己在做什么”，这是大工程中可用与否的分水岭。
5. **工具选型应匹配工作负载**：无工具在所有维度通吃，但对于需要高度自主、深度推理且必须接受治理的复杂开发，Claude Code 的 harness 架构是当前最完整的选择。

### 导师备课笔记

**核心概念**

1. **Agent Harness（代理缚具）**  
   这不是模型，而是把模型变为可操作环境、调用工具、管理记忆的“身体与中枢神经”。它包含工具注册、执行引擎、上下文管理器、安全护栏等九个组件。改变 harness，同一模型可以产生 6 倍的性能差异。

2. **决定论 Hook —— 上下文外的安全网**  
   Hook 是插入代理生命周期的可控断点，例如在写文件前（`PreToolUse`）运行 lint。关键是它**不在模型上下文内运行**，因此是确定性的；它可以**阻断并改写操作**，而不是仅仅事后通知。这弥补了纯靠提示词不可靠的缺陷。

3. **上下文压缩与子代理隔离**  
   长任务中模型“失忆”不是窗口大小问题，而是压缩策略问题。Claude Code 在令牌占用达 80-90% 时方触发压缩，并优先保留关键信息；子代理获得干净窗口，只返回摘要给主会话。这防止了主上下文被临时推理污染，维持长期计划的清晰。

4. **模型-Harness 共生演化**  
   最新模型往往与自家 harness 的工具调用格式、反馈模式一同后训练。当它被搬到其他 harness 时，工具逻辑与交互信号的差异会导致隐藏的性能回归。这是一种结构性护城河。

**关键区分点**

- **Hooks 的阻断能力**：Claude Code 的 Hook 可阻止操作并修改参数；Cursor 只能观察不可拦截。这是能否实现强制性合规（如 lint 失败就不让写）的分界线。
- **压缩触发的时机**：Claude Code 在上下文高负荷时才压缩，且保留结构化关系；Cursor 的压缩策略更易丢失跨文件类型依赖，导致玩家频繁重新提示。
- **扩展的成本模型**：Claude Code 把 Hook（零上下文成本）、Skill（轻量）、MCP（按需）、子代理（隔离加摘要）分成四级，其他工具缺少这种对上下文窗口的精细账本。

**常见误解**

1. **“差距主要在模型”**：多数人认为性能差异源于模型智商，忽略了 harness 的结构性作用（可差 6 倍）。
2. **“大窗口就解决了记忆”**：学生常假设上下文越长越好。实际上，不恰当的压缩与没有隔离，长上下文反而会引入更多噪音，让代理遗忘任务目标。
3. **“安全只要在 prompt 里说就行了”**：靠自然语言约束模型是不确定的。真正的安全需要 Hook 这样上下文外、可拒绝执行的硬机制。

**前置知识**

学生需了解：语言模型的工具调用/函数调用机制、上下文窗口和令牌限制、基础 agent 循环（感知-计划-行动）。最好有使用至少一种 AI 编程工具完成多文件任务的亲身困惑。

### 提问方向

**方向一：为什么会“忘事”？**
- **引导问题**：你让 AI 助手重构一个涉及多个文件的模块，刚开始它处理得挺好，可后来它把之前改过的类型关系弄反了，仿佛忘记了之前的工作。除了模型记忆容量，你觉得它“失忆”还可能和系统的什么设计有关？
- **期望学生自己发现的结论**：系统的上下文压缩时机与策略决定了哪些信息会被保留；没有子代理隔离的话，中间推理过程会把关键的早期信息挤出窗口。优秀 harness 会在高负载时才压缩，并用子代理返回摘要来保持主任务清晰。

**方向二：提示词能让 AI 绝对安全吗？**
- **引导问题**：你想让代理“提交前必须通过测试，失败了就停止”。你在 prompt 里写得清清楚楚，这足够可靠吗？如果模型在这步“不小心”还是提交了，有什么结构能彻底防止？
- **期望结论**：提示词是概率性的，不可靠。必须有一个运行在模型上下文之外的决定论 Hook，能在操作前拦截并阻断，才真正构成安全护栏。

**方向三：为什么不能只用一种方式扩展？**
- **引导问题**：我们有 Hook、Skill、MCP、子代理这么多扩展方式，看起来很乱。为什么不能全部用 MCP 工具搞定？提示：每一次调用工具、每一段工具描述，对模型的上下文窗口有什么影响？
- **期望结论**：不同扩展方式的上下文成本不同。Hook 执行在上下文外，几乎零成本；Skill 是轻量注入；MCP 的工具描述和返回结果都会消耗宝贵的窗口。因此需要按任务成本分级选用，而不是一刀切。

**方向四：换平台为什么不灵了？**
- **引导问题**：某款模型在自家工具里处理文件特别厉害。如果有人把它接入另一个编辑器代理，它会自然保持同样强的表现吗？如果打折扣，原因可能出在哪里？
- **期望结论**：模型很可能与原生 harness 的工具调用模式和反馈信号进行了联合后训练。换了 harness，工具接口和交互逻辑不同，模型就像“换了一副不合适的假肢”，性能会退化。这就是模型与 harness 的共生护城河。
