# Claude Code Agent Harness 架构优势分析  
**内部技术备忘录**  
*仅限内部传阅 · 2026-07*

## 1. 什么是代理 harness，为什么它决定成败
大语言模型只做推理，不执行动作。将推理转化为文件读取、终端命令、代码写入的那一层软件，就是 **代理 harness**（Agent Harness）。它包含九类核心组件：模型接口、工具注册、上下文管理、规划模块、执行引擎、记忆系统、反馈回路、安全护栏和编排层 [R1-2]。

Harness 不是包装器，而是 **模型能力的倍增器**。实践表明：相同模型搭配不同 harness，任务完成质量最多相差 6 倍 [R1-18]。更进一步，模型会在特定 harness 中后训练，优化该 harness 最常用的工具操作（文件系统、bash、子代理调度），因此更换 harness 可能导致能力退化 [R1-5]。

## 2. 四款工具的架构定位：一张表讲清根本差异

| 维度 | Claude Code | Cursor | Copilot | Devin |
|------|-------------|--------|---------|-------|
| **交互界面** | 终端 CLI | IDE 深度集成 | IDE 集成 | Web/云 IDE |
| **架构哲学** | 最大模型自由度 + 丰富操作 harness [R2-17] | 内嵌代理 + 内联补全双模式 [R2-4] | 带约束的代理模式，深度绑定 GitHub [R1-9] | 云端全自主，预定义计划-执行 [R1-3] |
| **上下文窗口** | 200K，百万 token 可用 [R2-18] | 宣传 200K，实测 70–120K [R2-12] | 受 IDE 通信限制 | 全仓库克隆，无交互压缩 [R2-14] |
| **扩展机制** | Hooks + Skills + MCP + Subagents/Teams [R2-8] | 仅 MCP，无 hooks/自定义代理框架 [R1-10] | MCP 有限，依赖 Copilot Extensions | 几乎不可扩展 |
| **长程自主能力** | 强：单会话完成大型重构，可后台运行 [R2-12][R2-13] | 中：云代理可后台，但大任务易丢失上下文 [R2-12] | 弱：代理模式最不成熟，需频繁干预 [R1-12] | 强：仅限定义明确的异步任务 [R1-11] |
| **安全模型** | 本地运行，逐项请求明确同意 [R1-3] | IDE 内允许/拒绝 | GitHub 权限体系 | 沙箱容器，事后审计 |

## 3. 设计哲学：自由度与控制的取舍
主流代理框架（LangGraph、Devin）通过显式图节点或多步规划器来编排行为。Claude Code 反其道而行——**给予模型最大决策自由度，将工程精力全部投入工具层的健壮性** [R2-17]。它不约束模型的推理路径，只确保文件系统、shell、子代理等工具有清晰合约和可靠执行。其结果：对于需要动态调整策略的复杂任务（如重构类型系统、跨模块错误定位），Claude Code 一次会话即可完成，而 Cursor 因上下文断裂需要反复重新提示 [R2-12]。

这种设计不是否定控制的价值，而是把控制从“流程编排”转移到“事件拦截”——下文将看到，hooks 系统在不侵入推理链的前提下提供了精细控制。

## 4. 上下文管理的三层铠甲
长任务的第一杀手是上下文污染和溢出。Claude Code 的 harness 实现了三层防护：

- **压缩层**：上下文使用达 **80–90%** 时自动触发压缩，将早期工具输出和对话精简为关键摘要 [R2-11]。Cursor 的压缩阈值和算法不同，长任务中更易丢失关键关联 [R2-11]。
- **接力层（Ralph Loop）**：当模型试图提前退出但目标未完成，harness 截获退出信号，在干净上下文中重新注入任务描述，让模型读取上一次迭代留在磁盘的状态继续工作 [R1-16]。这解决了持续任务的“半途而废”问题。
- **隔离层**：子代理 (subagent) 拥有独立上下文，完成任务后只返回**摘要**，主会话不吸收日志噪声 [R2-20]。多代理团队 (Agent Teams) 通过共享任务列表并行工作，无需中央编排器，避免单点上下文膨胀 [R2-19]。

## 5. 分层扩展：四种机制覆盖“成本谱系”
Claude Code 同时提供 Hooks、Skills、MCP、Subagents/Teams 四种扩展机制。这不是设计冗余，而是因为**不同扩展对上下文窗口的成本不同**，单一机制无法覆盖从零成本到高成本的全部需求 [R2-8]：

| 扩展机制 | 上下文成本 | 适用场景 | 其他工具支持情况 |
|----------|------------|----------|------------------|
| **Hooks** | 零（在模型上下文外运行） | 预提交检查、安全扫描、自动格式化 | Cursor 有基本 hooks，能力受限 [R2-9]；Copilot 无 |
| **Skills** | 低–中（按需注入提示模板） | 为模型提供可复用的领域知识 | 均无直接等同物 |
| **MCP** | 中（工具调用结果进入上下文） | 连接外部 API、数据库 | Cursor 支持，Copilot 有限 [R1-10] |
| **Subagents/Teams** | 高但隔离（独立上下文） | 并行任务、大规模代码库改造 | Cursor 3.0 八代理并行窗口，但缺乏共享任务队列 [R2-18][R2-19] |

Hooks 是这套体系的杀手特性。它们拥有 **20+ 生命周期事件**，支持阻止操作、注入信息、重写参数，全都在模型上下文之外执行 [R2-7][R2-10]。这意味着可以用完全不消耗 token 的方式叠加安全策略、质量门禁和工作流规则——其他工具目前做不到。

## 6. 安全与同意：终端驻留的人机契约
Claude Code 运行在开发者终端，对每个写入文件系统或执行命令的动作**请求明确同意** [R1-3]。这一设计的深层价值是：模型可以提出大胆方案，由人承担最终决策。Cursor/Devin 的云代理在后台执行时，这种即时把控被削弱，安全压力转移到事后审计 [R2-9][R2-13]。在金融、基础设施等强合规场景中，终端同意模型是更易达标的架构选择。

## 7. 不是万能药：架构优势与应用边界
Claude Code 在自主代理任务中确实拔尖，横向对比的共识是 **Claude Code > Cursor > Copilot** [R1-9]，它与 Cursor 均能自主完成全部 8 个测试文件，而 Copilot 需更多手动干预 [R1-12]。但它存在明确局限：

- **无 IDE 内联体验**：无法替代 Cursor 的 tab 补全和实时重构建议，日常快速编码时 Cursor 更顺手 [R1-7]。
- **上手门槛与成本**：需要命令行基础，长任务消耗 token 较多 [R2-1]。
- **多工具协调税**：若用 Claude Code 管后端、Cursor 管 UI，需手动同步 schema 和任务分发，工具本身不互通 [R2-15]。
- **Devin 的不可替代区间**：高清定义、重复性异步任务（版本升级、lint 清理）更适合 Devin 过夜执行，早间审查 PR [R2-16]。

**结论**：没有通吃的代理架构，只有最匹配工作流的架构。但若关注点在于**长程自主开发、复杂推理、扩展可控性和安全合规**，Claude Code 的 harness 设计在 2026 年的市场上建立了实质优势。

## 8. 关键收获
1. **Harness 是模型能力的倍增器**：相同模型因 harness 差距可产生 **6 倍** 性能差异 [R1-18]。
2. **自由 + 健壮工具 > 流程约束**：给予模型决策自由度，同时提供高质量工具层，在复杂任务中胜出 [R2-17]。
3. **上下文工程决定长跑能力**：压缩 + Ralph Loop + 子代理摘要构成长程记忆体系，是多文件无断裂操作的前提 [R1-16][R2-20]。
4. **扩展性按上下文成本分层**：Hooks（零成本）到 Teams（高但隔离）的频谱，让开发者用最小 token 成本获得所需控制 [R2-8]。
5. **架构与工作流匹配才是最优解**：理解每款工具的设计得失，才能在不同场景中做出正确选型。

### 导师备课笔记
**核心概念**  
1. **代理 harness**：将语言模型变成能操作文件、运行命令的智能体的那一层软件，包含工具、上下文、安全等。  
2. **上下文压缩与隔离**：在长任务中持续输送关键信息，丢弃噪音，通过压缩、子代理摘要和重启循环来维持长期连贯。  
3. **分层扩展性**：不同扩展对上下文窗口的成本不同——hooks 零成本，skills 低成本，MCP 中等，子代理高但隔离。理解为什么不能把所有扩展合并成一个机制。  
4. **同意模型**：终端本地代理执行危险操作前必须由人类批准，与云代理的自动执行形成对比。

**关键区分点**  
- **自由度 vs 控制流**：Claude Code 选择“让模型自由决策 + 丰富工具”；Devin/LangGraph 选择“规划器控制步序”。两者在长程复杂任务中的表现差异是讨论核心。  
- **上下文内 vs 上下文外**：hooks 运行在模型上下文之外，其他扩展在上下文之内——这个边界决定了 token 成本和安全审计的可行性。  
- **终端本地 vs 云代理**：本地同意模式提供即时人为判断，云代理的优势在于并行和异步，但安全管理滞后。

**常见误解**  
1. “Claude Code 强是因为模型强”——实际相同模型在不同 harness 中可差 6 倍，harness 架构同等甚至更重要。  
2. “Cursor 和 Claude Code 是同类产品”——Cursor 是 IDE 代理，Claude Code 是终端代理，协作模式与适用场景根本不同。  
3. “加更多约束会让代理更安全”——过度约束会削弱复杂任务的表现，侧载的 hooks 提供了不牺牲推理能力的控制手段。

**前置知识**  
学生需要了解：LLM 的基本工作方式（token、上下文窗口）；终端与 IDE 的区别；什么是 MCP；以及“工具调用”在 LLM 中的含义。建议先让学员亲手在 Claude Code 和 Cursor 中完成同一长任务，体验上下文丢失和同意机制的差异。

### 提问方向
**1. 引导问题**：如果你在两个不同的应用中用完全相同的模型完成同一个任务，一个表现优异另一个不断失败，可能的原因是什么？  
*期望学生发现*：差别不在模型，而在**软件层如何管理工具、上下文和安全**——即代理 harness 的决定性作用。

**2. 引导问题**：想象你有一个能读文件、写命令的 AI，但上下文窗口只能装下最近几分钟的对话。要让它完成一个 3 小时的编码任务，你会设计哪些机制让它“记住”该做什么，并且不被旧信息淹没？  
*期望学生发现*：需要**压缩老信息**、**允许任务在干净上下文中重启并读取最新状态**（Ralph Loop），以及**把子任务外包给独立上下文的工作者并只取回结果摘要**——这就是 Claude Code 的上下文管理方案。

**3. 引导问题**：如果一个代理系统提供了四种不同的扩展方式来添加功能，你会觉得这是设计冗余还是有意为之？什么情况下你会选择用 A 而不是 B？  
*期望学生发现*：不同扩展消耗的上下文 token 不同，有些根本不需要进入上下文就能执行（hooks）。为了在性能和成本之间取得最优解，需要**覆盖从零成本到高成本的全部选项**，单一机制无法满足所有需求。

**4. 引导问题**：让 AI 代理在做事前必须获得你的批准，有时会觉得烦。为什么还有人认为这是“更安全”的架构，甚至在企业中更受偏爱？  
*期望学生发现*：**终端同意模型**将高风险操作的最终决策权保留在人手中，免去了事后复杂的审计，也让代理可以更大胆地提出方案而无需内置过多猜疑逻辑，反而是解放了模型能力。

**5. 引导问题**：如果你有一个重复性高、定义清晰的任务（比如批量升级依赖），和一个需要边做边调整的复杂架构改动，你会交给同一个代理工具吗？为什么？  
*期望学生发现*：Devin 的云全自主模式适合前者（异步、批处理），Claude Code 的交互终端模式适合后者（动态推理、人工介入）。没有最好的架构，**只有最匹配任务属性的架构**。
